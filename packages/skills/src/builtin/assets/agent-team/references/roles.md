# 角色来源与派遣细节

## 角色来源（三种，按优先级）

1. **团队模板**（用户点名或队长推荐）：Prism 团队库 `~/.zcode/teams/*.md`（优先 `prism_team_list` / `prism_team_get`，MCP 不可用直接读文件）。模板给出编制与工作流，队长适配任务后使用；**模板正文声明「严格执行」时不做适配**——编制与工作流照原样使用，不增减、不换角、不虚拟兜底。
2. **子智能体库现选**（默认）：盘点 `~/.zcode/agents/` 与项目级 `.zcode/agents/`，读各文件 frontmatter 的 description，按「职责/适用于/不适用于」与岗位匹配。
3. **虚拟兜底**（库缺岗位）：`subagent_type: "general-purpose"` 承载，契约贴进 prompt（默认契约见文末附录）。

选角注意：有的角色带专属工具或技能白名单（挂 mcpServers 等），行为特性与普通 subagent 不同——看 description 判断是否匹配岗位，不匹配就换。

## 派遣模板（按来源二选一）

**A. 库内角色**（subagent_type = 角色名，契约已在它的系统提示词里，prompt 不必重贴）：
```
[任务]
你是 <角色名>，本次任务：<一句话任务>。
完成标准：<可验证的标准>。
范围边界：只做上述任务；范围外问题记录到输出文件「遗留问题」节，不顺手处理。

[工作流位置]
你处于第 <N> 阶段（<阶段名>）：上游 <角色>（读其输出 <文件>）；
你的输出 <文件> 由 <角色/阶段> 消费；受阻时 <回流路径>。

[输入] / [输出]
按顺序读：<路径：用途>…；结果写入 <路径>，格式：<结构>；
最终回复一句话结论（成功/失败/阻塞 + 关键发现）。
```

**B. 虚拟角色**（subagent_type = general-purpose，在最前面加一段）：
```
[角色契约]
你是 <岗位名>。<核心契约一句 + 裁决解释>。
职责：<…>；边界（禁止）：<…>。
```

## 派发原则（继承模板约定）

- **按独立性分桶，桶内合并**——派发前先分桶，再决定合并还是并行：
  - **同域小任务**（改同一批文件 / 同一模块的小修小补）→ 合并成一次派发（prompt 编号分条），省往返
  - **独立任务**（不同模块/目录、无共享文件、各自可独立验收）→ **拆开并行派发**，同角色多实例各接一桶（如 dev×2 按写域切流）；把独立任务串行塞给一个实例是双重浪费——并行度归零，交付被最慢桶拖死
  - **问答/探索类**（不改码的调研、分析、多问题排查）→ 按模块切分并行**只读**派发，同模块的问题合并进同桶
  - 判断口诀：**两个任务会不会写同一批文件？各自能不能独立验收？**——会写同一批 → 同桶合并；互不冲突且可独立验收 → 拆开并行
- 每次派发自包含（路径+关键决策摘要+上一步结论），不要「先问能不能做」再正式派。
- **任务单六要素，缺一不派**：目标 / 写域 / 验收标准 / 上下文 / 依赖 / 完成动作——粒度上限「单实例一次会话可完成」，超了先拆。
- **派发后验收**：回收时对照验收标准核对产物，不达标 SendMessage 打回该实例重做（计 rework）；没验收就标绿 = 流程造假。
- 文件是跨会话的可靠记忆：设计文档是唯一真相源，各角色读文件而非 prompt 转述全文；队长维护 `context.md`（关键决策+当前状态）随派发附上。

## 并行与串行

- 探索/开发类岗位可并行——同一消息块发多个 Agent 调用，或 `run_in_background: true`
- 审核岗串行在被审对象之后；测试岗在全部开发流完成之后
- 后台任务完成会收到通知，期间继续调度其他角色，不空等

## 会话复用（强制 · 登记制）

**默认复用，新建是例外。** 子代理每次新开都是全新会话、上下文归零；复用既有实例等于带着全部记忆继续干活。

| 场景 | 做法 |
|------|------|
| 同角色连续跟进（bug 修复、回归、复审、后续阶段衔接） | `SendMessage` 发给既有 agentId——**必须复用** |
| 一棒完成、实例空闲（Agent 调用已返回 / 后台完成通知已到） | **实例没死**——上下文仍在，`SendMessage` 直接续用；**不许新开 Agent 调用顶替** |
| 跨轮次（新一轮需求/无关新任务） | 可开新实例；开工前把上轮结论要点（黑板 context.md）copy 进 prompt |
| 实例死亡/超时 | 先 `SendMessage` 探活确认；确实死了才重建——从黑板文件（context.md + 该角色最近产物）恢复上下文，再补「当前状态速览」，不重新侦察 |
| 长任务不阻塞调度 | `run_in_background: true` |

判断标准：**下一步是否受益于它已经读过/做过的东西**。受益就复用（默认），无关才新开。

### 登记表 `.agent-team/agents.md`（每次派遣/汇报后更新，模板见 `templates/agents.md`）

| 岗位/角色 | 子代理 agentId | 最后动作/状态 |
|-----------|----------------|----------------|
| 开发流1 | agent_xxx | 修复 bug-2 完成，待复检 |

- **派遣时**：登记 agentId
- **汇报后**：更新「最后动作/状态」列
- **下一棒**：先查表拿 id 再派遣——同角色绝不无脑新开

## 升级链

任一开发角色同一问题尝试 2 次失败 → 队长整理「已试过什么、卡在哪」转攻关岗（库里最强的攻坚角色，或虚拟兜底「先证明，后攻坚」契约）。
攻关 spike 证明不可行 → 带证据请示用户（换路线/降需求/记技术债）。

## 缩编规则（默认按模板/选角满编，例外才缩编，向用户说明）

- 任务极小：1 开发 + 1 测试 + 1 审核，流程保留
- 纯调研：调研岗为主，可用只读的 Explore 类型省 token
- 简单文档任务：写作岗 + 审核岗各一

## 岗位分工速答

- 谁审设计/守门禁？**质量审核岗**（审出问题盯到修好才盖章；设计/需求等文档的修订归作者，审核岗不代改）；谁审局部代码？**评审岗**（只出问题清单，无门禁权）
- 谁能改代码？开发岗、攻关岗、测试岗（测试资产）、审核岗（仅代码 ≤5 行小修，记录进报告；文档类退回作者）
- 谁和用户说话？只有队长。角色把问题回报队长，由队长统一问用户

## 附录：虚拟兜底默认契约

| 岗位 | 核心契约 |
|------|----------|
| 开发 | 交付可运行的增量，绝不扩大战场 |
| 攻关 | 先证明，后攻坚 |
| 测试 | 没有运行证据的通过等于造假 |
| 质量审核 | 查出问题盯到修好才盖章（文档修订归作者） |
| 调研 | 每个结论都要可溯源 |
| 评审 | 只诊断，不动刀 |
| 写作 | 为读者写作，而不是为自己 |
