# Prism 角色定义需求文档（讨论稿 v0.1）

> 状态：**讨论稿，待继续确认**
> 日期：2026-09-09
> 范围：专家角色的定义格式与语义。团队定义另文。
> 原则：服从 **Prism 纯控制面定位**——Prism 只提供角色**定义**，不负责执行与调度。

---

## 1. 定位：角色是决策契约，不是岗位说明书

Prism 不执行 agent，所以它不需要完整的岗位说明书。它需要的是**可裁决的决策单元**——能被团队组合、被校验、被注入给宿主。

角色有三个层次：

| 层 | 绑定 | 回答 |
| :--- | :--- | :--- |
| 能力层 | Skill（白名单） | 它能**做什么** |
| 知识层 | 知识范围（层 + 可选书） | 它能**看到什么** |
| **决策层** | **核心第一原则** | 冲突时它**牺牲什么** |

**核心第一原则是角色的种子。** 没有原则的角色，在压力下会优化"看起来完成了任务"——顺手改点代码、跳过验证、把不确定说成确定。原则是让它停下来的东西。

---

## 2. 核心第一原则：五条检验

| # | 检验 | 反例 | 正例 |
| :--- | :--- | :--- | :--- |
| 1 | **可裁决**——两选项冲突时选一个 | "高质量交付" | "先证明可行再承诺" |
| 2 | **有张力**——遵守要付出代价 | "认真负责地完成任务" | "交付可运行增量，绝不扩大战场" |
| 3 | **域内专属**——只在本角色领域成立 | "安全第一"（人人都说） | "存疑即阻断：漏报可补，误放不可逆" |
| 4 | **可检验**——能判断是否被违反 | "追求卓越" | "没证据不放行" |
| 5 | **一句话**——写长就成职责描述 | 一段话 | 一行 |

> 关键在第 2 条：**原则如果从不逼你做痛苦的取舍，它就是装饰。** 检验方法：问"违反它会怎样"——若答案是"也没什么大不了"，那就是口号。

### 2.1 原则与团队仲裁链的关系

- **角色原则 = 局部裁决**：角色内部冲突时用。
- **团队仲裁链 = 全局裁决**：角色之间冲突时用（如 `安全 > 需求满足 > 质量一致性 > 进度`）。
- 两者必须**一致**；团队链优先，且矛盾应被检出。

Prism 据此提供**原则一致性检查**：
1. 每个角色是否有原则；
2. 原则是否与团队仲裁链冲突；
3. 是否有两个角色对同一决策都宣称最终话语权。

## 3. 定义格式（兼容既有 agent 格式）

### 3.1 文件位置

```
<PRISM_HOME>/roles/<role-id>/AGENTS.md     # Prism 原生
```

也可导入既有格式（见 §5）。

### 3.2 frontmatter

```yaml
---
name: security-auditor           # 必填，kebab-case，与目录名一致
description: >                   # 必填，职责 + 适用于 + 不适用于 + 与相近角色分工
  白盒安全审计角色。适用于：代码变更的漏洞审计。
  不适用于：业务逻辑修复（只给建议）、性能优化、代替 QA 收口。
color: red                       # 可选，UI 标识色
skills:                          # 能力白名单（未列出 = 不能用）
  - taint_trace
  - payload_generate
  - cve_query
knowledge:                       # 知识绑定（层 + 可选书）
  layers: [global, role]
  books:                         # 可选：限定具体书，省略 = 该层全部
    - security-redline
---
```

> **兼容性**：既有 agent 格式的 `model` / `thoughtLevel` / `injectAgentsMd` 字段仍被接受（导入时保留）。Prism 的推荐做法是把模型与思考档位放在**团队层**（环境属性，换宿主/配额就要变），而非焊死在角色定义里。

### 3.3 正文结构

```markdown
# 角色显示名

## 核心第一原则
**<一句话，可裁决、有张力、域内专属、可检验>**

<为什么是这条：它在什么冲突下做出什么牺牲。>

## 职责
- ...

## 边界（禁止）
- ...            # 边界比职责更重要——防止越界

## 协作位置
- 上游输入：...
- 下游消费者：...
- 受阻回流：...

## 完成判定
- <可检验的"做完了"，不是感觉>
```

### 3.4 字段说明

| 字段 | 必填 | 作用 | 备注 |
| :--- | :--- | :--- | :--- |
| `name` | ✅ | 角色标识 | kebab-case，与目录名一致 |
| `description` | ✅ | 派遣决策依据 | 四段式：职责/适用于/不适用于/分工 |
| `skills` | ✅ | 能力白名单 | 未列出 = 不能用（最安全） |
| `knowledge` | ✅ | 知识绑定 | 层 + 可选书 |
| 核心第一原则 | ✅ | 决策契约 | 正文首节 |
| 职责 / 边界 | ✅ | 做什么 / 不做什么 | |
| 协作位置 | 建议 | 团队工作流自动接线 | 上游/下游/回流 |
| 完成判定 | ✅ | 可检验的完成标准 | |
| `color` | 可选 | UI 标识 | |
| `model` / `thoughtLevel` | 可选 | 兼容既有格式 | 推荐放团队层 |

## 4. 完整示例

```markdown
---
name: security-auditor
description: >
  白盒安全审计角色。适用于：代码变更的漏洞审计、安全红线核查。
  不适用于：业务逻辑修复（只给修复建议）、性能优化、代替 QA 收口。
color: red
skills: [taint_trace, payload_generate, cve_query]
knowledge:
  layers: [global, role]
  books: [security-redline]
---

# 安全审计师

## 核心第一原则
**存疑即阻断：漏报可以补，误放不可逆。**

面对"疑似漏洞但不确定"时，这条原则明确选择阻断而非"再看看"。
代价是误报会打扰团队——这正是它的张力所在。

## 职责
- 对代码变更做白盒安全审计，输出带 CWE 编号与置信度的漏洞清单
- 核查变更是否触碰安全红线 TopN
- 为每个发现给出可执行的修复建议

## 边界（禁止）
- 不修业务逻辑（只给建议，修复由开发执行）
- 不做性能优化
- 不代替 QA 做交付总审

## 协作位置
- 上游输入：dev 的代码变更
- 下游消费者：QA 终审
- 受阻回流：升级队长

## 完成判定
- 每个发现带 CWE 编号 + 文件:行号 + 置信度 + 修复建议
- 无发现的检查项也须列出检查范围（证明查过）
```

## 5. 导入既有 agent 格式

Prism 提供导入器，把 `~/.zcode/agents/*.md` 转成 Prism 角色定义。

| 既有字段 | Prism 处理 |
| :--- | :--- |
| `name` / `description` / `color` | 直接保留 |
| `model` / `thoughtLevel` / `injectAgentsMd` | 保留（标记为"环境属性"） |
| `## 核心契约` | 映射为 `## 核心第一原则` |
| `## 职责` / `## 工作方式` / `## 边界（禁止）` | 直接保留 |
| — | 补充 `skills`（白名单，导入时为空待填） |
| — | 补充 `knowledge`（默认 `layers: [global, project]`） |
| — | 补充 `协作位置` / `完成判定`（若正文缺失则留空待填） |

**导入不覆盖原文**，只生成 Prism 角色定义；原文保留在源目录。

---

## 6. 校验规则

| 校验 | 说明 |
| :--- | :--- |
| 必填字段完整 | `name` / `description` / `skills` / `knowledge` / 核心第一原则 |
| `name` 与目录名一致 | 防止引用错乱 |
| Skill 白名单可解析 | 引用的 Skill 必须已安装（否则警告） |
| 知识层合法 | `layers` ⊆ {global, project, role} |
| 原则存在且非空 | 缺失则角色不合格 |
| 原则与团队链不冲突 | 见 §2.1 |
| 无重复角色名 | 全局唯一 |
