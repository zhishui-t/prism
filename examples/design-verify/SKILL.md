# Design Verify — 设计文档开发前验证（指挥手册）

你是**流程指挥**（主会话）。职责三件事：锚定两端真相 → 调度机器与独立实例查中间 → 把必须由人做的三个决策交给人。你不代替人裁决，也不让作者会话复核自己的文档。

**核心命题**：AI 写的设计文档让 AI 审，只能审出「自洽」，审不出「真相」——同上下文的实例互相只会点头。本流程把验证从「判断对错」（需要业务知识）改造成「核对证据」（机器可查 + 人抽查）：绝大多数设计文档错误不是业务判断错，而是**对现状的错误信念**（引用不存在的符号、误解模块职责、把没实现当成已实现），这类错误不需要懂业务就能查。

**开工前先判路径（判错全错）**：

| 路径 | 触发条件 | 跑哪些 |
| :-- | :-- | :-- |
| **全流程** | 新子系统 / 数据迁移 / 破坏性接口变更 / 核心交易链路 / **接手后第一份设计文档** | 第 0 → 5 步 |
| **轻量** | 日常增量改动 / 非核心模块 / 局部重构 | 第 1 步（锚点核查 + 质检点）+ 第 4 步（门禁，可简化为 verdict.md 汇总 + 一行裁决） |

## 工作目录 `.design-verify/`（文件黑板）

项目下建 `.design-verify/`，各步产物落盘 = 该步完成；断点恢复时读黑板续跑，不重问已定的结论。

```
.design-verify/
├── behavior-contract.md   # 第 0 步：行为契约（业务真相或其代理）
├── anchors.md             # 第 1 步：锚点账本（机器可查，templates/anchors.md 格式）
├── verdict.md             # 第 1 步：机械核查裁决表（脚本产出）
├── semantic-review.md     # 第 1 步：语义层复核意见（独立实例产出）
├── trace-matrix.md        # 第 2 步：追溯矩阵 + 缺口登记
├── redteam-report.md      # 第 3 步：红队报告
├── backlog.md             # 文档债务 backlog（第六类缺口等，只记不堵）
└── gate.md                # 第 4 步：门禁裁决（人签）
```

**状态判定与压缩恢复（状态在黑板，不在记忆）**：每步完成与否由文件机械判定，不依赖对话记忆——

| 步 | 完成证据（文件） |
| :-- | :-- |
| 0 | behavior-contract.md 存在，且确认栏有记录**或**有降级声明 |
| 1 | verdict.md 存在且 BLOCKER=0 + semantic-review.md 存在（内联自核时标注在 verdict） |
| 2 | trace-matrix.md 存在且核心链路断头路清零 |
| 3 | redteam-report.md 存在且 P0 清单每条有处置 |
| 4 | gate.md 有三态勾选与人签 |
| 5 | gate.md 复验记录有新增行 |

对话记忆被压缩后：按上表从文件重建进度 → 重读本 SKILL.md 流程 → 向用户简报断点续跑。**不凭压缩摘要继续，不重问已定结论。**

## 六步流程

### 第 0 步：锁定业务真相源（不可跳过，不可 AI 替代）

SRS 没被业务确认之前，后面所有技术评审都是在验证一份可能错误的需求。二选一：

- **有专家**：把需求逐条拉回业务事实源（需求文档、工单、合同/法规、真实用户案例、历史故障记录）核对——每条需求必须有来源和可测试的验收标准；请专家对范围、角色权限、业务规则、非功能指标（要可度量，不是「性能良好」）签字确认，落 `behavior-contract.md` 确认栏。
- **无专家（接手陌生项目的常态）**：派只读子代理收集三类事实——**现有测试**逐个断言的行为（测试是前任维护者留下的业务真相编码）、**git log** 关键决策与原因、**系统实际运行行为**；你执笔蒸馏成**一页行为契约**（模板 `templates/behavior-contract.md`），每条标来源（test / commit / probe / unverified），刻意设计与历史包袱分开标注。拿这一页去找干系人确认——确认一页是可行的，通读 50 页设计是不可行的。找不到任何人确认时，在 gate.md 显式记录「业务真相未经人工确认」，第 4 步裁决上限锁定为 **Go with Gaps**，不假装拿到 Go。

业务知识可信度排序：测试 > git 历史 > 系统实际行为 > 文档 > 人的记忆。

### 第 1 步：事实锚定（把「凭空编造」扫掉——成本最低，拦截的错误最硬）

**0. 图优先解析符号（有代码图谱就先走这条）**：先 `prism graph status <项目名>`（MCP `prism_graph_status`）判三态——
**有图且不陈旧 → 用图谱**（`prism graph explain` 判符号存在性与位置，`path` 验调用链，`affected` 看影响面）；
**没图 → 降级 grep/文件锚点**；**陈旧图不信任**（行号偏移逐文件不规则——实测同一次查询里一个符号准确、另一个偏 6 行，无法整体校正，比没图更危险），重建或降级并在 verdict 记 `graph: stale`。
批量解析用 `node <本skill目录>/scripts/resolve-symbols.mjs "符号A,符号B" --project <名>`（退出码 3 = 应降级 grep）。
图谱只负责**语义定位**，给不出逐字引文——解析到的 `file Lnn` 仍要转写成文件锚点，由脚本逐字确证，两者互为交叉验证。细则见 `references/code-graph.md`。

1. **提取承重断言**：从设计文档挑出承重断言（挑选标准与格式见 `references/evidence-anchors.md`），逐条登记进 `anchors.md`（格式 `templates/anchors.md`，`##` 只留给锚点 id）。非承重内容（愿景、风格论述）不锚。
2. **机械层**：跑本 skill 自带脚本（**在项目根执行，或显式带 `--root <项目根>`**——否则相对路径全部 MISSING-FILE）——
   ```
   node <本skill目录>/scripts/check-anchors.mjs .design-verify/anchors.md --root <项目根> > .design-verify/verdict.md
   ```
   裁决分级：**BLOCKER** = FABRICATED / MISSING-FILE / FORMAT-ERROR / READ-ERROR（东西不存在或无法核查，必须修）；**动作项** = WRONG-LINE / COUNT-MISMATCH（东西在、锚点漂了，刷新锚点即可，不堵门禁）。
   退出码：**0 = 无 BLOCKER；1 = 存在 BLOCKER；2 = 用法/账本错误**（exit 2 时 stdout 为空，原因只在 stderr——先看去 stderr 的报错，别把用法错误当成门禁失败或通过）。
3. **语义层（独立实例）**：引文存在 ≠ 断言为真（「调用了某 API」≠「实现了某 API」，测试代码不算功能实现）——派**独立实例**（reviewer 角色，或挂 spec-vs-impl-checker 技能的实例；不得复用写文档的会话）逐条读上下文复核断言含义，产出 `semantic-review.md`。

   **派遣判定**（判据是「验证者与作者是否共享上下文」，不是创建成本——黑板模式下派发成本本来就有界）：

   | 情形 | 语义层 | 红队 |
   | :-- | :-- | :-- |
   | 本会话参与写文档 | 必须独立实例，无例外 | 永远新会话 |
   | 文档外部来 + 轻量小任务 | 可主会话内联自核，但 verdict.md 必须标注「语义层非独立实例」 | 永远新会话 |
   | 任何情形 | 机械层永远脚本（天然独立） | 只给决策清单，不给原文 |

   没标注的内联 = 隐瞒降级，比降级本身严重。红队永远新会话的原因：主会话为提取决策清单必然读过设计原文，自己红队自己 = 没有红队——这不是成本问题，是定义问题。
4. **质检点（人，不可省）**：每批核查结果随机抽 **5 条 ✓** 由人打开文件亲自核对；发现 1 条误判 → **该批结果作废重跑**并检查工具配置（--root 路径、编码、锚点格式）。这是整条链上唯一由人直接执行的验证——没人抽查复核器，所有 ✓ 的成色都只是工具自述。

**门禁**：BLOCKER 清零 + 质检点通过。BLOCKER 的修复方向：改断言（文档错）或改设计（设计错），修完只复验修复项（见第 5 步）。

### 第 2 步：跨文档闭环（用追溯矩阵找断头路）

事实对了不等于设计闭环了。建追溯矩阵（模板 `templates/trace-matrix.md`，判读规则 `references/traceability.md`）：**跨你实际有的文档建**，两份也能建，不为了矩阵凑五份文档。正向对账可派 tester-whitebox（spec-vs-impl-checker 正是对账活）。**代码锚点列优先填图谱节点 id**（`prism graph explain` 的 `ID`），并用 `prism graph affected` 辅助判定哪些链路是核心（被广泛调用的枢纽节点 = 动它就动一片）。

六类缺口，处置不同：前五类（有需求无落点 / 有设计无需求来源=范围蔓延 / 有规则无技术落点 / 有决策无测试覆盖 / 有测试无代码分支）——**核心链路清零**，非核心显式登记为已知缺口；第六类（代码有逻辑但文档没写）——**只记不堵**，进 `backlog.md`：遗留项目里未文档化代码是常态，逐条审计是无底洞。

**门禁**：核心链路（动钱 / 动数据 / 安全 / 对外契约）断头路清零。

### 第 3 步：技术风险红队（AI 挑刺，人反证）

你从设计文档把关键技术决策整理成**固定格式清单**（决策 / 备选 / 选择理由 / 证据锚点 / 验证方式 / 置信度，表头见 `templates/redteam-report.md`）。派**新会话独立实例**做红队——不复用第 1 步实例、**只给决策清单不给设计原文**，按固定清单挑：事务边界 / 幂等去重 / 重试放大 / 缓存一致性 / 迁移回滚 / 可观测性 / 容量与降级。可选加强：跨引擎第二意见（如 WorkBuddy 引擎）——不同模型的错误不相关；**它是同一道门内的第二个意见，不是第二道门**（铁律 1 禁止的是同一维度装两套工具/流程，不禁止对同一清单换引擎复核一次）。

人工部分不可外包：对高风险横切点**抽样反证**（用 trace、schema、配置、探针测试去试图推翻；**有代码图谱时先用 `prism graph affected <节点> --depth 2` 圈定波及面，再用 `prism graph path` 追调用链**，比读文档快且不会被文档的措辞带偏），而不是逐条读文档。

**门禁**：P0 级技术风险每条有明确的验证方式或修复方案。

### 第 4 步：门禁裁决（人做，显式放行而非默认过）

按 `templates/gate-decision.md` 核对条件，人勾选三态之一：

- **Go**：业务真相已确认 + BLOCKER 清零 + 质检点过 + 核心链路闭环 + P0 有处置。
- **Go with Gaps**：非核心缺口已登记**负责人与期限**；无专家路径的上限就是本档。
- **No-Go**：业务真相未定（连代理契约都没有）/ 存在无法在开发前澄清的事实性冲突 / 技术不可行。No-Go 不是失败——它省下的是按错误文档开发的全部成本。

**文档写完 ≠ 通过**；没有显式签署的 gate.md，不开写业务代码。

### 第 5 步：修复与复验（闭环）

门禁未过的项走「修复 → 复验」，不是「改完就算数」。复验**只查被修复的锚点/条目及其直接影响面**（脚本 `--only A1,A3` 定向重查 + 独立实例定向复核），不做全量重跑。复验结果追加进 gate.md 复验记录。

### 交接（gate.md = Go 之后）

- **任务卡种子**：trace-matrix 每个闭环行 → tasks.md 任务卡（六要素对齐 agent-team 任务单：目标 / 写域 / 验收标准=spec 条目 / 上下文 / 依赖 / 完成动作）；六类缺口处置——①③④补齐任务（先补文档再开发）、②裁范围回需求、⑤修死测试、⑥进 backlog 不堵
- **开发后复验**：开发完成后锚点 `--only <修复涉及的id>` 定向复验——这是「**代码符合设计**」的机械证据，与 delivery 阶段 8 对账矩阵互为印证
- **黑板并入**：接 delivery 时 `.design-verify/` 产物并入 `.agent-team/`，gate.md 并入 `.design_ok` 证据链；独立使用时保持 `.design-verify/`
- 派遣判定（见第 1 步）同样适用于交接后的复核实例

## 工具与派遣

完整选型表（本地默认 + 外部后置 + 核实快照）见 `references/tooling.md`。铁律三条：

1. **同一道门只留一个**：同一维度跑两套工具/实例不是双保险，是重复评审。
2. **本地先行**：脚本机械层 + reviewer 独立实例 + spec-vs-impl-checker 今天就能全跑；外部工具（@nullius-inverba/claims、gsd-doc-verifier 等）是实测抓到本地漏掉的真问题后才替换该格的升级件，不提前采购。
3. **三方脚本运行前过目源码**（供应链卫生），外部工具信息以 `references/tooling.md` 核实快照为基线、装前自行复核。

## 人的三个位置（其余全部可自动化）

| 位置 | 做什么 | 为什么是人 |
| :-- | :-- | :-- |
| 第 0 步业务确认 | 确认行为契约/需求范围 | 业务对错工具无解——工具只能证明「文档与代码一致」，证不了「需求该不该存在」 |
| 第 1 步质检抽查 | 抽 5 条 ✓ 亲自开文件核对 | 复核器本身也要被验证，否则是 AI 给 AI 盖章 |
| 第 4 步门禁裁决 | Go / Go with Gaps / No-Go | 放行是担责动作；证据 AI 整理，结论不代填 |

## 与 agent-team 的关系

在 agent-team / delivery 流水线内，本 skill 可作为**卡点③（设计确认）质量审核**的执行手法（锚点核查替代泛泛评审，gate.md 并入 `.design_ok` 证据链）；独立使用时本流程完整自洽。`.design-verify/` 黑板与 `.agent-team/` 黑板并存互不干扰。端到端衔接总图（主干地图 + 工件链注册表 + 统一路由表）见仓库 `examples/pipeline.md`——不随本技能装配，属组合层文档。

## 硬性约束

- **两端锚死，中间才可信**：第 0、1 步是全流程的地锚——这两步的质量决定第 2、3 步的意义；跳过地锚跑后面的步骤是在沙子上盖楼
- BLOCKER（东西不存在或无法核查）不清零不过门禁；WRONG-LINE / COUNT-MISMATCH 是动作项，不把维护噪音当门禁失败
- 复核者与作者必须不同实例；红队实例不得继承任何前序上下文
- 质检点不可省、不可由 AI 代做
- 裁决只能人做；无专家路径必须显式降级，不假装拿到 Go
- 任何修复走「修复 → 复验」闭环；复验只查修复项与影响面
- 冲突裁决链：**安全 > 业务真相 > 事实正确 > 进度**——事实层的问题不许用「先开发后补文档」折中
