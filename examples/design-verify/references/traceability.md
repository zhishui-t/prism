# 追溯矩阵 — 跨文档闭环与六类缺口

> 第 2 步的操作手册。事实对了（第 1 步），不等于设计闭环了：需求可能没有落到设计，功能可能找不到技术落点，测试可能覆盖了根本不存在的分支。

## 1. 建矩阵（跨实际有的文档，不预设层数）

- 层取自项目**实际工件**：需求（SRS/issue/任务书）→ 设计（FDD/设计文档）→ 技术决策（TDD/ADR）→ 测试（用例/测试文件）→ 代码锚点（anchors.md 的 id）
- **两份文档也能建矩阵**；为了凑五层而让 AI 生成三份中间文档没有意义——五份全是 AI 写的话，中间层的矩阵只是 AI 追 AI，可信度全靠两端（第 0 步业务真相、第 1 步代码证据）的地锚
- 每条需求一行，状态列标「闭环 / 缺口类型」；正向对账（需求→代码逐条认领）可派 tester-whitebox 挂 spec-vs-impl-checker 技能执行

## 2. 六类缺口：定义与处置

| # | 缺口 | 方向 | 处置 |
| :-- | :-- | :-- | :-- |
| ① | SRS 有需求，但无设计落点 | 正向 | **堵**——需求被悄悄丢了，LLM 最隐蔽的失败是静默缩水 |
| ② | 设计有功能，但 SRS 无来源 | 反向 | **堵或裁**——范围蔓延；确认是镀金就删，确属遗漏就补需求并回第 0 步 |
| ③ | 有业务规则，但无技术落点 | 正向 | **堵**——规则没有承载组件就是空头支票 |
| ④ | 有技术决策，但测试无覆盖 | 正向 | 核心链路**堵**；非核心登记为已知缺口 |
| ⑤ | 有测试用例，但代码无对应分支 | 反向 | **查**——可能是死测试（测了个不存在的行为），也可能是代码漏实现 |
| ⑥ | 代码有逻辑，但文档全没写 | 反向 | **只记不堵**——进 backlog.md |

**为什么第⑥类只记不堵**：接手的遗留项目里未文档化代码是常态不是例外，逐条审计等于重写全部文档，是无底洞。把它当文档债务排期，不当开发门禁。

## 3. 核心链路判定（缺口①③④的堵门范围）

满足任一即核心链路，断头路必须清零：

- **动钱**：交易、计费、结算、退款
- **动数据**：数据迁移、schema 变更、数据删除/覆盖
- **安全**：认证、授权、越权边界、数据泄露面
- **对外契约**：公开 API、消息格式、文件格式、第三方集成

非核心链路的缺口可带病进入下一步，但必须显式登记进 gate.md 的缺口表（负责人 + 期限），不许静默放过。

## 4. 产出与门禁

- `trace-matrix.md`（模板 `templates/trace-matrix.md`）：矩阵 + 缺口登记（类型/位置/处置）
- `backlog.md`：第⑥类与其他文档债务（位置、现状、发现日期）——只记不堵，进后续排期
- **门禁**：核心链路①③④清零；②⑤全部有结论（补/删/修）；非核心缺口全部显式登记
