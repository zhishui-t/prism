# 角色来源与派遣细节

## 角色来源（三种，按优先级）

1. **团队模板**（用户点名或队长推荐）：Prism 团队库 `~/.zcode/teams/*.md`（优先 `prism_team_list` / `prism_team_get`，MCP 不可用直接读文件）。模板给出编制与工作流，队长适配任务后使用。
2. **子智能体库现选**（默认）：盘点 `~/.zcode/agents/` 与项目级 `.zcode/agents/`，读各文件 frontmatter 的 description，按「职责/适用于/不适用于」与岗位匹配。
3. **虚拟兜底**（库缺岗位）：`subagent_type: "general-purpose"` 承载，契约贴进 prompt（默认契约见文末附录）。

选角注意：有的角色带专属引擎或工具（挂 mcpServers、走 WorkBuddy 引擎等），行为特性与普通 subagent 不同——看 description 判断是否匹配岗位，不匹配就换。

## 派遣模板（按来源二选一）

**A. 库内角色**（subagent_type = 角色名，契约已在它的系统提示词里，prompt 不必重贴）：
```
[任务]
你是 <角色名>，本次任务：<一句话任务>。
完成标准：<可验证的标准>。
范围边界：只做上述任务；范围外问题记录到输出文件「遗留问题」节，不顺手处理。

[工作流位置]
你处于第 <N> 阶段（<阶段名>）：上游 <角色>（读其输出 <文件>）；
你的输出 <文件> 由 <角色/阶段> 消费；受阻时 <回流路径>。

[输入] / [输出]
按顺序读：<路径：用途>…；结果写入 <路径>，格式：<结构>；
最终回复一句话结论（成功/失败/阻塞 + 关键发现）。
```

**B. 虚拟角色**（subagent_type = general-purpose，在最前面加一段）：
```
[角色契约]
你是 <岗位名>。<核心契约一句 + 裁决解释>。
职责：<…>；边界（禁止）：<…>。
```

## 派发原则（继承模板约定）

- **能合并不拆分**：同一角色的多个任务合并成一次派发（prompt 里编号分条），每次派发自包含（路径+关键决策摘要+上一步结论），不要「先问能不能做」再正式派。
- 文件是跨会话的可靠记忆：设计文档是唯一真相源，各角色读文件而非 prompt 转述全文；队长维护 `context.md`（关键决策+当前状态）随派发附上。

## 并行与串行

- 探索/开发类岗位可并行——同一消息块发多个 Agent 调用，或 `run_in_background: true`
- 审核岗串行在被审对象之后；测试岗在全部开发流完成之后
- 后台任务完成会收到通知，期间继续调度其他角色，不空等

## 实例复用规则

| 场景 | 做法 |
|------|------|
| 同角色连续跟进（bug 修复、回归、复审） | `SendMessage` 发给既有 agentId——带着记忆继续 |
| 跨阶段新任务、需要干净上下文 | 开新实例 |
| 长任务不阻塞调度 | `run_in_background: true` |

判断标准：**下一步是否受益于它已经读过/做过的东西**。受益则复用，无关则新开。

## 升级链

任一开发角色同一问题尝试 2 次失败 → 队长整理「已试过什么、卡在哪」转攻关岗（库里最强的攻坚角色，或虚拟兜底「先证明，后攻坚」契约）。
攻关 spike 证明不可行 → 带证据请示用户（换路线/降需求/记技术债）。

## 缩编规则（默认按模板/选角满编，例外才缩编，向用户说明）

- 任务极小：1 开发 + 1 测试 + 1 审核，流程保留
- 纯调研：调研岗为主，可用只读的 Explore 类型省 token
- 简单文档任务：写作岗 + 审核岗各一

## 岗位分工速答

- 谁审设计/守门禁？**质量审核岗**（审出问题直接修，修好才盖章）；谁审局部代码？**评审岗**（只出问题清单，无门禁权）
- 谁能改代码？开发岗、攻关岗、测试岗（测试资产）、审核岗（针对性修复，记录进审核报告）
- 谁和用户说话？只有队长。角色把问题回报队长，由队长统一问用户

## 附录：虚拟兜底默认契约

| 岗位 | 核心契约 |
|------|----------|
| 开发 | 交付可运行的增量，绝不扩大战场 |
| 攻关 | 先证明，后攻坚 |
| 测试 | 没有运行证据的通过等于造假 |
| 质量审核 | 查出问题就修好，修好才盖章 |
| 调研 | 每个结论都要可溯源 |
| 评审 | 只诊断，不动刀 |
| 写作 | 为读者写作，而不是为自己 |
