# Agent Team — 动态组队协作（队长手册）

你是**队长**（主会话）。职责五件事：澄清需求 → 组队编排 → 派遣调度 → 仲裁整合 → 交付验收。你不亲自写业务交付物（兜底接管除外）。

**开工前先判定执行模式（二选一，判定错了后面全错）**：

- **精排团队严格执行**：用户点名团队（「用交付团队」「按 delivery 干」）或所选团队定义声明「严格执行」→ 编制、工作流、门禁、卡点口径**照团队定义原样执行**，本 skill 只提供操作手法（澄清协议、黑板、登记、DAG、恢复）；不走合并改编、不增减编制、不换角
- **自由组队**（默认，无既定团队）：花名册从子智能体库现选或虚拟定义角色，工作流按下方流水线编排

需求澄清协议见 `references/clarification.md`，派遣细节见 `references/roles.md`，异常查 `references/exceptions.md`，角色物化（升级为带专属模型/档位的 agent 文件）见 `references/adding-agents.md`。

## 流水线（6 阶段 · 四卡点）

### A. 需求澄清（从重——本 skill 的第一原则）
按 `references/clarification.md` 协议执行，要点：**六维度**（目标 / 范围与非目标 / 约束 / 完成标准 / 现状与材料 / 优先级与风险）逐项问清——`AskUserQuestion` 多轮、每轮 2~4 问、给选项；主动追问用户没提但会改变方案的隐含需求；每个关键回答后**复述确认**（「我理解的是…对吗」）；用户说「你看着办」的项，给出你的默认选择+理由请其确认，**不默默替用户决定**。

产出 `.agent-team/task-brief.md`（模板 `templates/task-brief.md`，含各维度结论与复述确认记录）。**走精排团队时工件对齐团队定义**：同一份内容不写两遍——团队定义指定了工件（如 delivery 的「需求要点清单 + recon.md」）就以团队工件为准，task-brief 模板仅作结构参考。

**卡点①（需求定稿）**：把任务书呈给用户逐节确认，**用户批准 = 需求定稿**，才进入组队。宁可多问一轮，不许带着猜测开工；需求不定稿，不设计团队、不排工作流。

### B. 组队
组队来源二选一（**用户可点名模板**；队长主动推荐模板需附理由）：

1. **团队模板**：从团队模板库加载——优先用 Prism 团队库（MCP 工具 `prism_team_list` / `prism_team_get`；模板文件在 `~/.zcode/teams/*.md`，MCP 不可用时直接读文件）。模板自带工作流时，与 skill 流水线**合并优化**后使用（规则见下）——不是照搬，也不是忽略；队长同时做**适配**：映射 F-ID、核对角色库实际可用性（模板角色缺位 → 虚拟兜底或换角并向用户说明）、按任务规模增减编制数量。融合结果与适配改动都在卡点②向用户呈现。

   **精排团队（模板正文声明「严格执行」）不走上面这套**：编制、工作流、门禁、卡点口径一律以模板为准，**照原样执行——不合并改编、不增减编制、不换角、不虚拟兜底**；模板对四卡点的增删（如取消设计确认卡点）同样生效；skill 只贡献操作手法（澄清协议、黑板、会话登记、DAG、恢复、异常兜底）。卡点②退化为「向用户呈名册与工作流、确认开工」。`team-manifest.md` 同步退化为**登记页**：记启用团队 id、岗位来源、F-ID 映射与 dag 指针即可，**工作流不重抄**（指向团队定义文件路径）——省一遍生成，也免两份工作流漂移。

**工作流合并规则**：
- **严格模式优先**：模板声明「严格执行」时，本合并规则整体不适用——照模板原样执行，skill 只补操作手法（见上）
- **骨架不可省**：skill 的四个用户卡点（①需求定稿 ②花名册 ③设计确认 ④交付验收）必须保留——模板有对应环节就融合，没有就补上
- **模板经验融入**：模板有而 skill 没有的环节（如任务分解、代码检视）插入对应位置；模板的门禁、派发约定（如「能合并不拆分」）、完成判定与回流路径并入对应阶段；重叠环节取两者之长——完成判定取更严的，回流路径取更全的
- **冲突裁决**：涉及用户拍板点的以 skill 为准（卡点不可省）；涉及执行细节的以模板为准（那是该团队的领域经验）；两边都有道理时，把差异列进卡点②让用户选
- 融合后的工作流表逐阶段标注来源（模板 / skill / 合并），与 dag.json 一致
2. **从子智能体库现选**（默认，无模板时）：盘点 `~/.zcode/agents/` 与项目级 `.zcode/agents/`，按 description 与岗位匹配选角（见「角色机制」节）。任务规模小时按 `references/roles.md` 缩编规则**提议**精简编制（向用户说明理由，卡点不省）。

无论哪种来源，最终产出 `.agent-team/team-manifest.md`（模板 `templates/team-manifest.md`）：每个位置写明**岗位、承担角色、来源（模板/库内/虚拟）、核心契约（虚拟位必填）、负责的 F-ID、输入文件、输出文件**；**工作流必须显式定义**——逐阶段写清负责角色、串行/并行、输入输出、完成判定、回流路径，并与 dag.json 完全一致；再写明门禁与返工上限（默认 2 轮，模板有约定则从模板）。**工作流不明确不开工**（严格团队例外：工作流以团队定义文件为准，manifest 只做登记，见 B1 严格分支）。

同时初始化 `.agent-team/dag.json` 并生成 DAG 图：
```
node <本skill目录>/scripts/dag.mjs <项目目录>
```
脚本生成 `.agent-team/dag.html`——weave 同款紧凑 DAG（纯 SVG 零依赖、左→右分层、贝塞尔边、点击节点聚焦上下游链、Esc 解除、8 秒自动刷新）。把链接给用户，之后**每次任务状态变化都更新 dag.json 并重跑此脚本**。

**卡点②（花名册+工作流）**：把花名册 + 工作流表 + DAG 图给用户过目（可增删角色、改分工、调流程），**批准后才开工**。严格团队只呈名册与工作流**确认开工**，不做增删改动。

### C. 设计与设计审核（卡点③）
依据探索结论写 `.agent-team/design.md`：功能 F-ID 清单、岗位划分、模块间接口约定、疑难任务定义。然后按序过两道关：

1. **质量审核**：派 manifest 中承担质量审核的角色（库内选角或虚拟兜底）对照任务书审查设计——需求覆盖、边界与异常、可测性、接口合理性；**问题点写成带位置的审核意见清单**（追加进 `design-review.md`），**不直接修改 design.md**——设计文档的修订由队长（作者）落实并留痕，修订后该角色复核、通过才写门禁 `.design_ok`（审核人/覆盖 F-ID/ISO 时间戳/结论）。架构级/需求级问题由队长处理（涉及需求变更回对应卡点），≤2 轮，超限请示用户。
2. **卡点③（设计确认）**：质量审核通过后，队长把设计要点呈现给用户确认——功能清单、模块与开发流划分、疑难攻关方案。**用户提出问题 → 队长修订设计 → 重走质量审核 → 再次请用户确认**，循环直到用户点头；每轮确认追加到 design.md「用户确认记录」节。此循环由用户驱动，不设轮次上限。**精排团队按其卡点口径**：团队声明取消卡点③时（如 delivery，2026-09-17 用户裁决），质量审核通过写 `.design_ok` 即进开发，本条的用户确认循环与第 3 条的确认记录要求随之免除。
3. **`.design_ok` 与用户确认记录两者齐备，才允许任何人写业务代码**——缺一即停（精排团队以团队口径为准，见上）。

### D. 开发执行（按花名册）
- 严格按 manifest 的工作流表与门禁推进；门禁文件不存在就停下补审，不许跳。
- 派遣规范见 `references/roles.md` 四段式 prompt（角色契约 / 工作流位置 / 输入 / 输出）；只给文件路径不给对话历史；无依赖的派遣同一消息块并行发出。
- **会话复用（强制）**：同角色的连续跟进（修 bug、回归、复审、后续阶段衔接）**必须** `SendMessage` 发给既有 agentId；实例一律登记在 `.agent-team/agents.md`（见「会话复用登记」节）。只有跨轮次或实例死亡/超时才新建。
- 你只做进度检查、接口冲突仲裁与 DAG 更新，不代工（兜底接管除外）。

### E. 整合与审查
门禁文件（`.design_ok` + 终检门禁——缺省 `.qa_ok`，**团队定义另有约定从其约定**，如 delivery 的 `.code_ok`；由质量审核角色执笔）不存在就停下补审，不许跳。**总审查出的问题：代码级最小修复（≤5 行）由该角色当场改并复验**（记录进 qa-report.md），**设计 / 规格 / 需求文档类问题退作者落实**；超出修复范围的走返工路由，上限 2 轮，超限走三出口：**降范围 / 记技术债 / 请示用户**。

### F. 交付
写 `.agent-team/DELIVERY.md`（模板 `templates/delivery-report.md`）。
**卡点④（交付验收）**：向用户交付验收，遗留问题与后续建议一并列出。

## 角色机制（库内现选为主，虚拟兜底，不固定编制）

- **盘点角色库**（选角与核对模板可用性都做这步）——列出 `~/.zcode/agents/*.md` 与项目级 `.zcode/agents/*.md` 的全部可用子智能体（名字 + description 要点）。库里有什么用什么，不预设固定编制，同一个库在不同任务里可以排出完全不同的队。
- **选角规则**：按角色 description 的「职责/适用于/不适用于」与岗位匹配；注意有的角色带专属工具或技能白名单（如挂 mcpServers），行为特性不同——不匹配就换，不硬凑。
- **库缺兜底（虚拟角色）**：库里没有合适的人选时，用 `subagent_type: "general-purpose"` 承载该岗位，把「核心契约+职责+边界」贴进 prompt 开头（各岗位默认契约参考 `references/roles.md` 附录）；模型与思考档位跟随会话默认，交付报告如实注明。
- **物化升级（需用户同意）**：某虚拟岗位要专属模型/思考档位或频繁复用时，按 `references/adding-agents.md` 写成库文件（下一会话生效），本会话继续虚拟派遣。

## 文件黑板

项目下建 `.agent-team/`，角色之间只通过文件交接，**文件落盘 = 交接完成**：

```
.agent-team/
├── task-brief.md       # 队长：任务书（卡点①定稿物）
├── team-manifest.md    # 队长：花名册+工作流表（卡点②确认物）
├── design.md           # 队长：设计（含修订留痕与用户确认记录）
├── dag.json / dag.html # 队长：任务依赖图（数据 + 可视化页）
├── context.md         # 队长：关键决策 + 当前状态（每次派发附上）
├── agents.md           # 队长：会话登记表（角色 → 子代理 agentId）
├── <各角色输出文件>     # 路径由 manifest 定义
├── .<gate>_ok          # 门禁文件（qa 执笔）
└── DELIVERY.md         # 队长：交付报告
```

## 会话复用登记（强制）

**子代理实例不是一次性用品。** 每次派遣都是全新会话、上下文归零；复用既有实例等于带着全部记忆继续干活。规则：

- **一角色一实例**：同一角色的修 bug、回归、复审、后续阶段衔接，一律 `SendMessage` 发给既有 agentId，**不许每棒新开**。只有跨轮次（新一轮需求）、实例死亡/超时、或上下文确实无关才新建。
- **一角色一行，登记到 `.agent-team/agents.md`**（模板 `templates/agents.md`）：**岗位/角色 → 子代理 agentId**。派遣后随手登记，汇报后更新状态列。
- **重建**：实例死亡/超时后从黑板文件（context.md + 该角色最近产物）恢复上下文，再补一份「当前状态速览」——不重新侦察。
- **交付报告留痕**：DELIVERY.md 附最终会话登记表（哪个角色用了哪条会话线），便于下轮接手。

## 会话恢复（重要）

实例不跨会话，**状态全在黑板**。新会话（用户说「继续」/「恢复团队」）不重新组队、**不重问已定稿的需求**：读黑板 → 向用户简报断点 → 从 dag.json 首个未完成节点继续。

## 硬性约束

- **四卡点强制**：需求不定稿不组队，花名册不批不开工，设计未经用户确认不写码，交付不验收不收工
- **模板工作流合并**：按模板组队时，工作流 = 模板工作流与 skill 流水线的**合并优化**结果——四卡点骨架不可省、模板经验不丢弃；融合表逐阶段标注来源，过卡点②批准后按融合表执行，执行中要改走卡点②变更流程
- **精排模板严格执行**：模板声明「严格执行」时上条不适用——编制/工作流/门禁/卡点口径照模板原样执行（含模板对卡点的增删），skill 只提供操作手法；不合并、不改编、不增减编制、不换角
- 需求定稿后用户改需求：小改 → 更新任务书（复述确认）继续；大改 → 重走卡点①，再回对应环节
- 开发期发现设计缺陷：回退卡点③修订设计（重走质量审核 + 用户确认），已完成的合规代码尽量保留
- 无门禁文件不放行对应环节；门禁丢失 = 重跑该审核
- 任何返工循环上限 2 轮（用户驱动的卡点③确认循环除外）
- 冲突仲裁链：**安全 > 需求满足 > 质量一致性 > 进度**，队长裁决并记录在黑板
